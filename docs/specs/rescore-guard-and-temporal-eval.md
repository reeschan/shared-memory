# rescore のガード、時間を含んだ評価、Web 画面での週次フィードバック

状態: 合意済み (2026-10-21)。用語は [GLOSSARY.md](../../GLOSSARY.md)、関連する決定は [ADR 0002](../adr/0002-rerank-before-rescore.md)。

分担: 前提にするのは、ブランチ `feat/stale-memory-search-eval` の仕様 `stale-memory-and-search-eval.md`。そちらが実装するのは次の範囲で、この仕様はそれを前提にする。

- 検索対象の tier を hot・warm・cold・archive のすべてにし、半減期を単一の値 90 日にする。
- search の各ヒットと get の応答に、freshness (作成からの日数・最後に読まれてからの日数・最終アクセス・古い記憶の印) を付ける。
- 状態の SQLite に検索ログ (search_log) と get のログ (get_log) を足す。記録するのは MCP の search / get と CLI の search で、90 日で消える。core に、期間を指定してログを読む関数を置く。
- 指標の計算 (nDCG@10・Recall@5・MRR@10・ブートストラップの 95% 区間) を core のモジュールにし、lab をコミットする。

`sm eval`、評価セット、週 1 回のフィードバック、通知 (トーストとレポート) は、**この仕様が受け持つ**。

画面の試作: [assets/search-feedback-mock.html](assets/search-feedback-mock.html) (design-studio の「実験ノート」の方向性、ダミーのデータ)。机上の検証のスクリプト: [assets/rescore-grid-sim.mjs](assets/rescore-grid-sim.mjs)。

## Problem Statement

検討の出発点は、「正解セットに対して検索がどれだけずれるかを測り、その結果で、個人に合わせた忘却曲線の設定 (半減期・decay_floor・access_weight・provenance_factor の組) を切り替える」という案だった。

調べた結果、**この案は今は妥当でない**。根拠は 2026-10-17 の評価データ (60 問、検索対象 309 メモリ) で行った机上の検証で、kNN 上位 50 チャンクに rescore を掛けるパラメーターのセット 720 通りを比べた。

1. **記憶の作成日の幅が短すぎて、半減期を測れない。** 評価の時点で、記憶の作成日は 8 日分 (10/10〜10/17) しかなかった。半減期 30 日だと、時間減衰の係数の差は最大でも 5% ほど。減衰の項だけを動かしたとき、順位が変わったのは 60 問中 0〜8 問で、nDCG@10 の差は 0.005 以下だった。
2. **差がつくのはアクセス回数の項だけで、しかも漏れがある。** kNN だけの近似では access_weight 0.2 で +0.013 だったが、本番の hybrid で測った実験では、弱めた rescore 全体で -0.025 だった。向きが一定しない。また、正解になった記憶は全体より多く読まれていた (読まれたことがある割合は、全体 0.34、合成の問いの正解 0.47、実クエリの正解 0.60)。実クエリは「エージェントが検索して get したもの」から作ったので、正解とアクセス回数が同じ出来事から生まれている。
3. **セットを選んでも、ノイズと見分けがつかない。** 上位 8 セットは同じ 0.880 に並んだ。5 分割の交差検証を 50 回繰り返すと、学習側で最良のセットを選んでも、検証側で今の設定を上回ったのは +0.003 だけだった (学習側では 0.005 よく見えていた分が楽観)。選ばれたセットは 250 回のうち 14 通りに散った。1 問の差は nDCG@10 で約 0.017 に当たり、決めておいた 2 つの設定を比べるだけでも、Δ0.01 を見分けるには約 60 問が要る。多くのセットから選ぶなら、60 問ではまったく足りない。
4. **評価セットが「今の記憶」に偏ると、鮮度の効きを測れない。** 正解の作成日は、評価セットを作った時期に集中する。また、新しい版と古い版が両方候補に入る問い (鮮度が効く問い) は、今の評価セットにはほとんど無い。

一方で、rescore が一次スコアの順位を悪くしていないかを見張る仕組みは無い。2026-10-17 には、本番の rescore が nDCG@10 を 0.884 から 0.694 に下げていたことに、実験をするまで誰も気づかなかった。週 1 回のフィードバックで判定を集める仕組みも、まだ形が決まっていない。

## Solution

- **パラメーターの自動の最適化と、名前付きのセットの定期的な入れ替えはしない。** rescore の式とパラメーターは、元のブランチで決めた形 (半減期は単一の 90 日、日数に対して単調、decay_floor 0.7) のまま固定する。
- **`sm eval` を作る。** 本番の検索 (`searchMemories` と config.yaml) で評価セットを測り、結果をレポートに書く。週 1 回、定期実行する。評価セットは評価のディレクトリ (設定で選ぶ。この利用者の環境では Proton Drive) に置き、ラベルの出どころ (エージェント / 人) を記録する。
- **`sm eval` にガードを入れる。** 本番の設定と「一次スコアだけ」を毎回同じ評価セットで測り、問いごとの差をブートストラップして 95% 区間を出す。rescore が有意に悪くしている状態が 2 回続いたら、トーストとレポートで知らせる。設定は人が変える。
- **評価とフィードバックでの読み出しは、アクセスに数えない。**
- **時間を含んだ評価にする。** 問いごとに「問われた時点」を持たせ、その時点の検索対象・置き換えの状態・アクセス回数を再現して測る。鮮度が効く問いに印を付け、別に集計する。正解の作成日の分布をレポートに載せる。
- **週 1 回のフィードバックを、ローカルの Web 画面で受ける。** トーストか `sm feedback` から、MCP サーバーのプロセスが配る画面がブラウザーで開く。グラフで今の状態を見ながら判定し、確定ボタンで結果が MCP サーバーのプロセスに送られる。判定の材料には、本番の設定と一次スコアだけを混ぜたリスト (インターリービング) を使う。
- **パラメーターの調整を見直す条件を決めておく。** 条件がそろったときだけ、名前を付けた候補 3 つまでを、時刻で分けた後ろ側で 1 回比べ、人が承認して変える。

## User Stories

1. 利用者として、rescore が検索の順位を悪くしていたら知らせてほしい。2026-10-17 のような劣化に、実験をしなくても気づけるようにするため。
2. 利用者として、知らせは、悪い状態が 2 回続いたときだけにしてほしい。1 回の偶然で通知が出続けないようにするため。
3. 利用者として、知らせが来ても、設定は自動で変わらないでほしい。何が変わったのかを自分で把握して決めるため。
4. 利用者として、レポートで、本番の設定と一次スコアだけの nDCG@10、その差、95% 区間を見たい。rescore がどれだけ効いているか (または害になっているか) を数字で知るため。
5. 利用者として、評価のたびの nDCG@10 の推移を見たい。検索の質が下がり始めたときに気づくため。
6. 利用者として、正解の作成日の分布と検索対象の作成日の分布を並べて見たい。評価セットが今の記憶に偏っていないかを確かめるため。
7. 利用者として、鮮度が効く問いだけの nDCG@10 と、「新しい方が古い方より上に来た割合」を別に見たい。鮮度の項に価値があるかを、それが効くはずの場面で測るため。
8. 評価の運用者として、問いごとに「問われた時点」を記録したい。その時点の状態で測り直せるようにするため。
9. 評価の運用者として、評価では、問われた時点より後に作られた記憶を検索対象から外したい。未来の記憶が正解を押しのける不公平を避けるため。
10. 評価の運用者として、置き換えの状態も、問われた時点のものを使いたい。その時点では有効だった記憶を正しく扱うため。
11. 評価の運用者として、get のログが溜まったら、アクセス回数も問われた時点の値で再現したい。アクセスの項を、漏れなしに測るため。
12. 評価の運用者として、評価やフィードバックで記憶を読んでも、アクセス回数と最終アクセスが増えないでほしい。評価セットに入った記憶ほどアクセスの項で有利になる漏れを防ぐため。
13. 評価の運用者として、評価とフィードバックの読み出しは、検索ログと get のログにも書かないでほしい。ログを「エージェントが実際に使ったもの」だけにして、問いの選び方とアクセスの再現を汚さないため。
14. 利用者として、`sm eval` が週 1 回自動で走り、結果がレポートに残ってほしい。手で回さなくても検索の質を追えるようにするため。
15. 利用者として、`sm eval` を手でも打ちたい。設定を変えた直後に確かめるため。
16. 評価の運用者として、lab にある今の評価セット (60 問) を、ラベルの出どころ「エージェント」として新しい評価セットに引き継ぎたい。最初から 60 問でガードを動かすため。
17. 利用者として、Windows 以外の PC では、トーストの代わりにレポートの場所とフィードバックの URL を表示してほしい。通知の仕組みが無くても使えるようにするため。
18. 利用者として、週 1 回のトーストをクリックしたら、フィードバックの画面がブラウザーで開いてほしい。CLI を打たずに始めるため。
19. 利用者として、`sm feedback` でも同じ画面を開きたい。トーストを見逃した週にも判定できるようにするため。
20. 利用者として、CLI は画面を開いたら終わってほしい。ターミナルを待たせずに済むため。
21. 利用者として、画面の上で、nDCG@10 の推移・ガードの差と区間・インターリービングの累計の勝ち負け・正解の作成日の分布をグラフで見たい。判定を始める前に今の状態をつかむため。
22. 利用者として、1 回の判定は 10 問までにしてほしい。数分で終えられるようにするため。
23. 利用者として、その週にエージェントが実際に投げた問いを、優先して判定したい。実際の使われ方に沿って評価セットを育てるため。
24. 利用者として、上位が 2 つの設定で同じになる問いは、判定に出さないでほしい。勝ち負けが付かない判定に時間を使わないため。
25. 利用者として、実クエリが足りない週は、評価セットの未判定の候補で 10 問を埋めてほしい。判定の機会を無駄にしないため。
26. 利用者として、結果のカードで、タイトル・抜粋・作成日・出所・古い記憶の印を見たい。判定に要る情報を 1 か所で見るため。
27. 利用者として、カードごとに「答えている / 一部関係する / 関係ない」を 1 クリックで選びたい。迷わず速く判定するため。
28. 利用者として、カードに「新しい版があり、これは古い」の印を付けたい。鮮度が効く問いの材料を自分の判断で足すため。
29. 利用者として、どの設定から出た結果かは伏せてほしい。判定が設定への思い込みで偏らないようにするため。
30. 利用者として、進み具合 (何問中何問か) を常に見たい。あとどれくらいで終わるかを知るため。
31. 利用者として、1 件選ぶたびに下書きとして保存され、タブを閉じても続きから再開できてほしい。途中で離れても判定を失わないため。
32. 利用者として、未判定の問いが残っていても確定できてほしい。忙しい週でも、判定した分だけは残すため。
33. 利用者として、確定ボタンを押したら、結果が MCP サーバーに送られ、完了の画面が出てほしい。送れたことを確かめるため。
34. 利用者として、確定したら直せないことを、確定の前に知らせてほしい。うっかり確定しないため。
35. 利用者として、判定の保存先 (評価セットとセッションの記録) を設定で選びたい。自分の環境 (例えば Proton Drive) に合わせて置くため。
36. 利用者として、判定が評価セットに「人の判定」として、セッション ID と時刻つきで残ってほしい。エージェントが付けたラベルと区別できるようにするため。
37. 利用者として、インターリービングの勝ち負けと、どちらの設定から出た結果かの割り当ても、セッションごとに残ってほしい。あとで集計をやり直せるようにするため。
38. 利用者として、何週分か貯めた勝ち負けで、本番の設定と一次スコアだけのどちらが良いかを符号検定で見たい。少ない判定数でも、比べた結果に意味があるかを知るため。
39. 利用者として、エージェントが「人の判定」を名乗ってラベルを書けないようにしてほしい。評価セットの信頼を保つため。
40. 利用者として、画面は外部に記憶の本文を出さずに動いてほしい。共有メモリの中身を外に漏らさないため。
41. サーバー集約構成の利用者として、クライアントの PC からも SSH トンネル越しに同じ画面を開きたい。どの PC からでも判定できるようにするため。
42. 利用者として、別の PC やブラウザーの別のタブから、他人のセッションを確定できないようにしてほしい。合言葉を知っている画面からだけ受け付けるため。
43. 利用者として、パラメーターの調整を見直す条件 (作成日の幅・人の判定の数・ガードの警告など) がそろったら、レポートで知らせてほしい。調整を検討する時期を逃さないため。
44. 利用者として、見直すときは、名前を付けた候補 3 つまでを、時刻で分けた後ろ側で 1 回だけ比べたい。選びすぎによる過学習を避けるため。
45. 利用者として、比べた結果で設定を変えるときは、自分が承認して config.yaml を変えたい。変更の責任を自分で持つため。

## Implementation Decisions

### パラメーターの調整はしない (今は)

- rescore の式とパラメーターは、元のブランチの仕様のまま。この仕様は式に手を入れない。
- 設定のセットを名前で持つ仕組み、評価の結果から自動で選ぶ仕組みは作らない。
- 見直す条件は次の 3 つが **すべて** そろったとき。条件の判定はレポートに出す。
  - (a) 検索対象の作成日の幅が、半減期の 2 倍以上 (半減期 90 日なら 180 日以上)。
  - (b) 人が判定した問いが 150 問以上あり、そのうち鮮度が効く問いが 30 問以上ある。
  - (c) ガードが警告を出した、または鮮度が効く問いで「新しい方が上に来た割合」が低い (目安は 0.6 未満)。
- 見直すときの手順: 前もって名前を付けた候補を 3 つまで用意する (一次スコアだけ / 今の設定 / 候補 1 つ)。問われた時点で並べた後ろ側 3 割だけで 1 回比べ、差の 95% 区間が 0 をまたがず、かつ差が 0.01 以上のときだけ採用を検討する。人が承認して config.yaml を変える。候補を足して何度も比べ直すことはしない。

### 評価セット

- 置き場所は評価のディレクトリ (設定で選ぶ)。既定は正本のディレクトリの隣の `eval/`。この利用者の環境では正本が Proton Drive にあるので、評価セットも Proton Drive に置かれる。
- 形は 1 行 1 問の JSONL (lab の評価セットの形を広げたもの)。1 問は、問いの ID、問い、問われた時点、種類 (合成 / 実クエリ)、正解 (メモリの ID と段階 2 / 1 の組)、鮮度が効く問いの印、ラベルの記録を持つ。ラベルの記録には、出どころ (エージェント / 人)、付けた時刻、フィードバックのセッション ID (人のときだけ) が入る。
- 同じ問いに人とエージェントのラベルがあるときは、人のラベルを使う。
- 引き継ぎ: lab の評価セット (60 問) を、出どころ「エージェント」として取り込む。問われた時点は、実クエリなら Query Insights の時刻、取れなければ評価セットを作った 2026-10-17 にする。合成の問いも 2026-10-17 にする。

### `sm eval` の実行

- 評価は、本番の `searchMemories` と config.yaml を使い、core の関数を直接呼ぶ。MCP の get は通らない (get はアクセスの記録と get_log を必ず書くため)。指標と区間の計算は、元のブランチが core に置くモジュールを使う。
- 結果は、評価のディレクトリに、実行ごとのレポート (人が読む Markdown) と、実行の履歴 (1 行 1 回の JSONL) として書く。履歴は、画面のグラフ (nDCG@10 の推移とガードの推移) の材料になる。
- 定期実行は、既存の定期タスクの仕組み (register-tasks.ps1) に週 1 回のタスクを足す。週 1 回の gc のあとに `sm eval` を走らせ、続けてフィードバックのセッションを作って通知する。
- 通知: Windows ではトーストを出す。中身は、ガードの判定、本番の nDCG@10、見直す条件の判定。トーストをクリックすると、作っておいたフィードバックのセッションの URL がブラウザーで開く。Windows 以外の PC では、レポートの場所とフィードバックの URL を標準出力に出す。サーバー集約構成では、サーバー PC で通知する。

### ガード

- `sm eval` は、毎回 2 つの構成を同じ評価セットで測る。1 つは本番の設定 (config.yaml の rescore あり。リランクが有効ならそれも含む)、もう 1 つは一次スコアだけ (rescore なし。リランクの有無は本番に合わせる)。
- 問いごとの nDCG@10 の差 (本番 − 一次スコアだけ) を、対応のあるブートストラップ (5,000 回) で 95% 区間にする。lab の比較と同じ方法。
- 警告の条件: 区間の上端が 0 未満の評価が 2 回続いたとき。通知は上の「`sm eval` の実行」のトーストとレポートで行う。
- インターリービングの累計 (下記) で、一次スコアだけが本番に有意に勝っている (符号検定で p < 0.05) ときも警告する。
- ガードは設定を変えない。

### アクセスの数え方

- 評価 (`sm eval`) とフィードバックの画面が記憶を読んでも、access_count と last_accessed_at は増やさない。検索ログと get のログにも書かない。アクセスとログを書くのは MCP の search / get と CLI の search なので、評価とフィードバックは core の検索と読み出しの関数を直接呼び、そこを通らない。
- これで、ログは「エージェントと人が実際に使った検索」だけになる。フィードバックの問いの選び方と、アクセス回数の再現 (第 2 段) はこのログを材料にする。

### 時間を含んだ評価

- 評価セットの問いは「問われた時点」を持つ。実クエリは検索ログ (search_log) の時刻、合成の問いは作った時刻。フィードバックで判定した問いは、その実クエリの時刻。
- 評価では、問われた時点の状態を再現する。
  - 第 1 段: 問われた時点より後に作られた記憶を検索対象から外す。置き換えの状態は、置き換えた側の作成日で、その時点のものを決める。時間減衰の「今」は、問われた時点にする。
  - 第 2 段 (get のログが溜まってから): アクセス回数と最終アクセスを、get のログから問われた時点の値で計算し直す。get のログは 90 日で消えるので、再現できるのは問われた時点から 90 日前までのアクセスに限られる。その範囲の外は、評価の時点の値で補い、そう補ったことをレポートに書く。第 1 段のあいだは、アクセス回数は評価の時点の値を使い、レポートに「アクセスの項は漏れを含む」と書く。
- **鮮度が効く問い**: 候補の上位に、同じ話題の古い版と新しい版の両方が入っていて、新しい版が正解である問い。印の出どころは 2 つある。置き換え (supersedes) でつながった組が候補に両方入る問いには、自動で印を付ける。フィードバックで利用者が「新しい版があり、これは古い」を付けた結果が入った問いにも付ける。
- レポートには、全体の nDCG@10 に加えて、鮮度が効く問いだけの nDCG@10、「新しい方が古い方より上に来た割合」、正解と検索対象の作成日の分布 (週ごと) を出す。

### インターリービング

- やり方は team-draft interleaving。2 つの順位 (本番の設定と一次スコアだけ) から、1 件ずつ交互に取って 1 つのリストを作る。毎回コインを投げて、どちらが先に取るかを決める。それぞれは、まだリストに入っていない自分の最上位を出す。リストは 10 件まで。乱数の種はセッションに記録し、同じ種なら同じリストになる。
- 問いごとの勝ち負け: 「答えている」を 2 点、「一部関係する」を 1 点として、それぞれが出した結果の点を足し、多い方の勝ち。同じなら引き分け。
- 集計: 引き分けを除いた問いで符号検定 (二項検定) をする。何週分も貯めて判断する。
- 期待してよい効き目: 利用者がリストの全件に段階を付けるので、その判定から両方の nDCG も直接出せる。つまり、クリックで比べるときほど判定数は減らない。ここで効くのは次の 3 点。1 問に見せる件数を 10 件に絞れること。どちら由来かを伏せて偏りを減らせること。上位が違う問いだけを選び、情報のある問いに判定を集中できること。判定は評価セットにも入り、ガードの母数を増やす。
- 判定に出す問いの選び方: その週の実クエリ (core の期間指定の関数で検索ログから読む。呼び出し元は MCP) のうち、2 つの設定の上位 10 件が違うものを優先する。2 つの順位は、セッションを作るときに、問われた時点の状態で測り直す。10 問に足りなければ、評価セットの未判定の候補で埋める。同じ問いが何度も問われていれば 1 問にまとめる。

### フィードバックの流れ

- 起動: 週 1 回のタスクが `sm eval` のあとに `sm feedback --notify` を走らせ、セッションを作ってトーストを出す。トーストのクリックでその URL が開く。手で始めるときは `sm feedback` で、既定のブラウザーで画面の URL を開いて終わる。どちらも結果を待たない。セッションは CLI が core の関数で評価のディレクトリにファイルとして作る。MCP サーバーのプロセスはそのファイルを読んで画面を配るだけで、セッションを作る HTTP の道は持たない (外からセッションを作られないようにするため)。
- 画面と受け口は、MCP サーバーのプロセスが同じポートで受け持つ。`/mcp` (JSON-RPC) とは別の HTTP の道を足す (セッションの画面、下書きの保存、確定)。**MCP のツールとしては公開しない。** 公開すると、エージェントが「人の判定」を名乗ってラベルを書けるため。
- セッションは作るときに 1 回限りの合言葉 (トークン) を持ち、URL に入れる。下書きと確定は合言葉が合うときだけ受ける。画面と受け口が同じオリジンなので、CORS は開けない。今の Host ヘッダーの確認はそのまま効く。
- 下書き: 1 件判定するたびにサーバーに保存する。開き直すと続きから再開できる。
- 確定: 判定を評価セットに書き、インターリービングの割り当てと勝ち負けをセッションの記録に書き、セッションを閉じる。確定したあとの下書きと確定は拒む。未判定の問いは判定なしとして扱う。完了の画面を出す。
- サーバー集約構成: クライアントの PC から、SSH トンネルで同じポートを転送して開く。`sm feedback` は開く URL を表示する。

### 保存先

- 評価セット・セッションの記録・レポート・実行の履歴は、すべて評価のディレクトリに置く (上の「評価セット」を参照)。
- 判定のラベルは、出どころを「人」とし、セッション ID と時刻を付ける。エージェントが付けたラベルと同じ評価セットに混ぜるが、出どころで区別できる。
- セッションの記録には、選んだ問い、乱数の種、2 つの設定の順位、混ぜたリストとどちら由来かの割り当て、判定、勝ち負けを入れる。
- SQLite には検索ログと get のログだけを置く (元のブランチのとおり)。下書きは評価のディレクトリのセッションの記録に書く。

### 画面

- 見た目は design-studio の方向性「実験ノート」(紙のような暖色の地、罫と余白、角丸と影なし、見出しは Playfair Display、本文は Noto Serif JP、数字は IBM Plex Mono)。テーマはコントラストの点検を通っている (ライト・ダークとも 15/15)。
- 構成: 上の帯 (セッションと確定ボタン)、見出しと 4 つの要約 (ガード・本番の nDCG@10・インターリービングの累計・評価セットの問い数)、結果の一覧 (グラフ 4 つ)、判定 (進み具合のバー、10 問の一覧、1 問分のカード)、確定の欄。配置は試作のとおり。
- グラフ 4 つ: nDCG@10 の推移 (本番と一次スコアだけの 2 本の線)、ガードの差と 95% 区間 (週ごとの区間を横に並べた図。0 の線と悪化の側を塗り分ける)、インターリービングの勝ち負け (週ごとの積み上げの棒)、正解の作成日の分布 (検索対象と正解の週ごとの割合)。
- 判定のカード: 番号、タイトル、抜粋、作成日、出所、スコープ、古い記憶の印 (元のブランチが付ける freshness の印を、問われた時点で計算し直したもの)。2/1/0 を選ぶ 3 つのボタン、「新しい版があり、これは古い」のチェック。どちら由来かは出さない。
- 本番では外部の読み込みをしない。試作は design-studio の決まりで Tailwind の CDN と Google Fonts を読んでいるが、本番ではテーマを素の CSS の変数にして同梱する (design-studio の `plainCssOf` と同じ変換)。フォントは同梱するか、端末のセリフ体に落とす。グラフはその場で SVG を描く。動き (選択・下書きの保存・確定) は同梱の小さな JS で行い、ビルドの手順は足さない。

### 評価の核のインターフェース (案)

評価の核は、検索の関数を外から受け取る形にする。`sm eval` は本番の `searchMemories` と config.yaml を渡し、テストは偽物の検索を渡す。

- 入力: 評価セット (問い・正解・問われた時点・鮮度が効く問いの印)、構成ごとの検索の関数、記憶の作成日と置き換えの情報。
- 出力: 構成ごとの問い単位の指標 (nDCG@10・Recall@5・MRR@10)、構成どうしの差と 95% 区間、ガードの判定 (警告 / なし)、鮮度が効く問いの指標、作成日の分布、見直す条件の判定。

## Testing Decisions

- よいテストは外から見える振る舞いだけを確かめる。内部の関数の分け方や、保存のファイルの書き方には依存しない。
- **合意済みの seam** (下流の実装はここでテストを先に書く):
  1. **評価の核**: 評価セット・構成ごとの検索の関数・記憶の情報を渡し、問いごとの指標、差の 95% 区間、ガードの判定、鮮度が効く問いの指標を確かめる。検索は偽物で差し替える。指標と区間の計算そのものは元のブランチの core のモジュールのテストに任せ、ここでは組み合わせ方を確かめる。確かめること: 問われた時点より後の記憶が除かれること。人とエージェントのラベルがあるとき人のラベルが使われること。置き換えの状態がその時点のものになること。区間の上端が 0 未満のときにだけ悪化と判定されること。2 回続いたときだけ警告になること。鮮度が効く問いで「新しい方が上に来た割合」が正しく出ること。前例は `search-memories.test.ts` (偽物の OpenSearch とリランカーで searchMemories を外から確かめている)。
  2. **インターリービング**: 2 つの順位と乱数の種から、混ぜたリストと割り当てを作り、割り当てと判定から勝ち負けと符号検定の p 値を出す。純関数として確かめる。確かめること: 同じ種で同じリストになること。両方の上位が同じなら引き分けになること。重複を出さないこと。10 件で止まること。
  3. **フィードバックの HTTP**: MCP サーバーのプロセスを、一時ディレクトリを保存先にして立ち上げ、外から確かめる。確かめること: セッションを作れること。下書きが保存され、開き直すと戻ること。確定で評価セットとセッションの記録に書かれること。合言葉が違うと拒むこと。確定したあとの下書きと確定を拒むこと。フィードバックで記憶を読んでも、アクセス回数が増えず、検索ログと get のログにも書かれないこと。`/mcp` のツールの一覧にフィードバックの書き込みが無いこと。前例は `server.int.test.ts`。
- `sm eval` と `sm feedback` の CLI は、seam 1 と seam 3 を呼ぶだけの薄い層にする。新しい seam は足さない。トーストと定期タスクの登録は自動では確かめない。
- 画面の見た目は自動では確かめない (E2E は作らない)。試作の HTML と見比べて人が確かめる。

## Further Notes

- 机上の検証は kNN だけで候補を作った近似 (rescore なしで 0.867。本番の hybrid では 0.884)。OpenSearch が止まっていたため。アクセス回数の項の向きが hybrid の実験と食い違ったのは、この近似のせいもありうる。結論 (減衰の項は測れない、セットの選択はノイズ以下) は、近似の差に左右されない。再現: `node docs/specs/assets/rescore-grid-sim.mjs lab/data` (lab/data は Git の管理外)。
- 鮮度の項が効くのは、(1) 同じ話題で古い版と新しい版があり、置き換え (supersedes) で明示されていないとき、(2) 検索対象の作成日の幅が半減期に比べて十分長いとき、の 2 つがそろう場面に限られる。例えば評価セットの s11 (TanStack Start 移行の第 1 段と v2 の完了メモリ) がこれに当たる。この場面の問いが十分に集まるまで、鮮度の項の価値は判断できない。
- 用語の案 (元のブランチの GLOSSARY.md の変更と重なるので、そちらが入ってから足す):
  - **ガード**: rescore を掛けた順位が、一次スコアだけの順位より有意に悪くなっていないかを見張る評価。
  - **問われた時点**: 評価セットの問いが実際に問われた (または作られた) 時刻。評価はこの時点の状態で行う。
  - **鮮度が効く問い**: 候補に同じ話題の古い版と新しい版があり、新しい版が正解である問い。
  - **インターリービング**: 2 つの設定の順位を交互に混ぜたリストで、どちらが良いかを比べる評価の方法。
  - **フィードバックのセッション**: 週 1 回の判定の 1 回分。合言葉・選んだ問い・混ぜたリスト・判定を持つ。
