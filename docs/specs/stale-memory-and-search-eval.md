# 古い記憶を検索に残して知らせる・検索のログを残す

## Problem Statement

shared-memory は、最終アクセスから 30 日たったメモリを cold にし、検索の対象から外している。決定事項・制約・ハマりどころのように長く有効な知識でも、しばらく読まれないと、どれほど問いに合っていても見つからなくなる。見つからないので読まれず、読まれないので戻ってこない。

rescore の半減期は tier ごとに違う (hot 30 日、warm 60 日、cold 120 日、archive 365 日)。そのため、tier が変わる日 (7 日目、30 日目) にスコアが上がり、少し古いメモリが少し新しいメモリより上に来る。

一方で、古いメモリをそのまま検索に出すと、内容が今も正しいかどうかが利用者に分からない。検索の結果に載る日付は作成日だけで、古いことを示す印はない。

検索の質を確かめる材料も足りない。検索のログがないため、実際の検索で何が出て、何が使われたかを後から確かめられない。評価スクリプト (lab) はコミットされておらず、半減期などの値や rescore の式を手で写しているので、本番とずれている。

## Solution

- 置き換えられていないメモリは、tier によらずすべて検索に出す。古さはスコアを少し下げるだけにし、類似度を主役にする。半減期は 1 つの値にして、スコアが日数に対して単調に下がるようにする。
- 作成からの日数で「古い記憶」を判定する。search と get の応答に、古さの情報と印 (freshness) を付ける。エージェントは古い記憶を根拠に使うとき、日付を添えて「今も正しいか」をユーザーに確かめる。ユーザーの答えに応じて、確かめた内容で書き直す・新しい内容で置き換える・廃止する。
- 検索と get をログに残す。lab をコミットし、指標の計算と rescore を本番のコードと設定から読むようにする。定期評価とフィードバックは、別の仕様 (docs/specs/rescore-guard-and-temporal-eval.md) で扱い、このログと指標の計算を使う。

## User Stories

1. 共有メモリの利用者として、30 日以上読まれていない決定事項も検索で見つかってほしい。長く有効な知識を失わずに済むから。
2. 共有メモリの利用者として、問いに合うメモリは古くても上位に出てほしい。鮮度より内容の一致の方が大事だから。
3. 共有メモリの利用者として、ほぼ同じ内容のメモリが並んだときは、新しい方が上に来てほしい。置き換え忘れの古い版に引きずられないため。
4. 共有メモリの利用者として、少し古いメモリが少し新しいメモリより上に来る逆転をなくしたい。順位が理屈に合うようにするため。
5. 共有メモリの利用者として、置き換えられたメモリは今までどおり検索に出ないでほしい。古い版と新しい版が混ざらないため。
6. 共有メモリの利用者として、古い記憶が根拠に使われるときは、エージェントから日付付きで知らせてほしい。今も正しいかを自分で判断できるから。
7. 共有メモリの利用者として、「古い」を作成からの日数で判断してほしい。エージェントが一度読んだだけで印が消えると困るから。
8. 共有メモリの利用者として、どの PC で検索しても同じメモリに同じ印が付いてほしい。判定が PC ごとのアクセス記録に左右されないため。
9. 共有メモリの利用者として、出来事の記録は早めに、知識は遅めに古い扱いになってほしい。種類によって有効な期間が違うから。
10. 共有メモリの利用者として、自分が確かめた記憶は、古い扱いになるまでの期間を長くしてほしい。確かめ直す頻度を下げるため。
11. 共有メモリの利用者として、同じ記憶について 1 つの会話で何度も聞かれたくない。負担になるから。
12. 共有メモリの利用者として、「今も正しい」と答えたら、その記憶が新しくなり、しばらく聞かれないようにしてほしい。確かめた結果を無駄にしないため。
13. 共有メモリの利用者として、確かめた結果を Git に残したい。どの PC からも同じ状態が見えるようにするため。
14. 共有メモリの利用者として、「内容が変わった」と答えたら、新しい内容で置き換えてほしい。古い内容が検索に出続けないため。
15. 共有メモリの利用者として、「もう要らない」と答えたら、廃止の記録で置き換えてほしい。削除の手段がなくても検索から外せるため。
16. エージェントとして、検索の結果に作成からの日数・使われていない日数・古いかどうかを受け取りたい。ユーザーへの伝え方を自分で組み立てられるから。
17. エージェントとして、get の結果にも、読む前の時点の古さの情報を受け取りたい。get でアクセスが記録された後の値では判断できないから。
18. エージェントとして、古い記憶の扱い方をツールの説明と指示ファイルで知りたい。どのエージェントでも同じ振る舞いをするため。
19. CLI の利用者として、`sm search` の表示で作成日と古い記憶の印を見たい。エージェントを介さずに気づけるから。
20. 共有メモリの保守者として、検索のクエリ・返したメモリと順位・時刻を記録したい。実際の検索の質を後から確かめられるから。
21. 共有メモリの保守者として、検索の直後にどのメモリが読まれたかを後から結び付けられるようにしたい。使われた結果と使われなかった結果を区別できるから。
22. 共有メモリの保守者として、ログは 90 日で消えてほしい。ローカルの記録が増え続けないため。
23. 共有メモリの保守者として、ログへの記録に失敗しても検索は失敗しないでほしい。記録は補助だから。
24. 共有メモリの保守者として、lab の実験と、これから作る定期評価で、同じ指標の計算を使いたい。数値を比べられるから。
25. 共有メモリの保守者として、lab が絞り込み条件・半減期・rescore を設定ファイルと本番のコードから読んでほしい。本番とずれないため。
26. 共有メモリの保守者として、lab のスクリプトを Git に残したい。実験を再現できるから。
27. Mac/Linux で登録済みの利用者として、指示ファイルの文面を手で直す手順を知りたい。新しい文面が自動では届かないから。

## Implementation Decisions

### 検索の範囲と rescore

- `search.searchable_tiers` の既定を `[hot, warm, cold, archive]` にする。設定キーと tier による絞り込みのコードは残し、あとで絞り直せるようにする。置き換えられたメモリは、今までどおり `is_superseded: false` で除く。
- `search.half_life_days` を tier ごとの値から 1 つの数に変える。値は 90 日。rescore は tier を見ずにこの値を使う。経過日数の起点 (最終アクセス、なければ作成日)、`decay_floor` 0.7、`access_weight`、`provenance_factor` は変えない。
- 半減期の値は評価で決めない。メモリの作成日の幅が 8 日分しかなく、半減期を変えても指標に差が出ないため (別のセッションの机上検証。共有メモリ 01M5E7S0MKW8RFE0T2JXCS8QD8)。見直しの条件は別の仕様で決める。
- 設定ファイルに古い形 (tier ごとの値) が書かれていたら、読み込みのときに分かりやすいエラーで止める。黙って解釈しない。

### 古い記憶の判定 (freshness)

- 古さの情報 `freshness` を次の形にする。
  - `age_days`: 作成からの日数 (整数)
  - `idle_days`: 最終アクセス (なければ作成日) からの日数 (整数)
  - `last_accessed_at`: 最終アクセス日時。なければ null
  - `stale`: 古い記憶かどうか
- `stale` は `age_days >= after_days[kind] × provenance_multiplier[provenance]` のときに true にする。
- 設定は `search.stale` 節に置く。
  - `after_days: { episodic: 30, semantic: 180 }`
  - `provenance_multiplier: { human_confirmed: 3, agent_verified: 1, agent_inferred: 1 }`
- 判定は日付から計算する純粋な関数として core に置き、search・get・CLI のどこからでも同じものを使う。tier の値は判定に使わない (tier は 1 日 1 回の decay でしか変わらないため)。

### search と get の応答

- 検索結果の各ヒットに `freshness` を足す。既存のフィールドは変えない。値は OpenSearch のヒットに入っている作成日・最終アクセス日・出所から計算するので、問い合わせの形は変えない。リランクする経路でも、しない経路でも付ける。
- get の応答を `{ meta, path, body, freshness }` にする。`freshness` は、アクセスを記録する前の統計から計算する (記録した後では、使われていない日数が常に 0 になるため)。
- MCP の search と get のツール説明で、返すフィールドの一覧を直し、次の趣旨を足す: 「`freshness.stale` が true の記憶を根拠に使うときは、作成日を添えて古い記憶だとユーザーに伝え、今も正しいかを確かめる。同じ記憶について確かめるのは 1 つの会話で 1 回まで。答えに応じて、確かめた内容を `provenance: human_confirmed` と `supersedes` で書き直すか、新しい内容で置き換えるか、廃止の短いメモリで置き換える」。
- CLI の `sm search` の 1 行表示に作成日を足し、古い記憶なら末尾に `[古い記憶: N 日前]` を付ける。`--json` は検索結果の形のまま出す。

### 「まだ有効」「変わった」「廃止」の記録

- 新しいツールは作らない。今ある write と `supersedes` で表す。
  - 今も正しい: 同じ本文を `provenance: human_confirmed` で書き、元のメモリを `supersedes` で置き換える。作成日が今日になるので、古い記憶の印が消える。
  - 内容が変わった: 新しい内容を `supersedes` で書く。
  - もう要らない: 「〜は廃止した (理由)」という短いメモリを `supersedes` で書く。

### 検索のログ

- `state_db` (SQLite) にテーブルを 2 つ足す。
  - `search_log`: 時刻・呼び出し元 (mcp / cli)・クエリ・絞り込み条件 (scope / kind / tags / limit)・返したメモリの id と順位とスコア
  - `get_log`: 時刻・呼び出し元・メモリの id
- MCP の search と get、CLI の search で記録する。記録に失敗しても検索は失敗させず、標準エラーに出すだけにする。
- 「使われた」の結び付け (検索から 30 分以内に、その検索結果に入っていたメモリが get されたもの) は、記録の時点では行わない。読み出す側 (別の仕様の評価とフィードバック) で行う。読み出しの関数として、期間を指定して search_log と get_log を返すものを core に置く。
- 90 日より古いログは、毎日の decay の実行で消す。
- ログは PC ごとで、外には出さない。

### 指標の計算と lab

- 指標の計算 (メモリ単位の nDCG@10・Recall@5・MRR@10、2 つの結果の差のブートストラップによる 95% 区間) を core のモジュールにする。lab の評価スクリプトと比較スクリプトはこれを使う。
- lab の絞り込み条件・半減期・出所の係数・rescore の式は、設定ファイルと core の関数から読む。手で写した値をなくす。
- `lab/` のスクリプトをコミットする。`lab/data/` は Git の管理外のままにする。

### エージェントへの指示

- mcp-setup スキルの指示ブロック (Windows と Unix の 2 か所) と、それを書き込む登録スクリプトに、1 行を足す: 「古い記憶 (`freshness.stale`) を根拠に使うときは、日付を添えてユーザーに確かめる」。
- Mac/Linux で登録済みの環境には自動で届かないので、手で直す手順を README に書く。
- ユーザーのグローバル指示ファイルにも同じ 1 行を足す (リポジトリの外。実装の最後に人の確認を得て行う)。

### 文書と共有メモリ

- 設計書 (design.md の 5.2 と 6.2)、interfaces.md、README の MCP ツールの節、GLOSSARY.md を新しい振る舞いに合わせる。
- 共有メモリのうち、今の仕様を書いた 2 件 (「検索は hot か warm だけを対象にする」「降格は検索対象から外すだけ」) を、`supersedes` で新しい仕様に置き換える。

## Testing Decisions

- よいテストは外から見える振る舞いだけを確かめる。応答の形、順位、記録された行を見る。内部の関数の呼び方は見ない。
- 合意済みの seam:
  1. **core の検索関数** (`searchMemories`): 偽の OpenSearch を使い、検索の範囲、単調な減衰による順位、`freshness` の値を確かめる。前例は search-memories.test.ts と search.test.ts。
  2. **古さの判定関数と指標の計算関数** (core の純粋な関数): 日付・種類・出所の組み合わせごとの `stale`、nDCG / Recall / MRR / ブートストラップの値を確かめる。
  3. **MCP サーバー** (インメモリの MCP クライアントで search と get を呼ぶ結合テスト): get の `freshness` がアクセスを記録する前の値であること、search と get がログに残ることを確かめる。前例は server.int.test.ts。
  4. **CLI** (`sm search` を実行する結合テスト): 表示の作成日と古い記憶の印、ログへの記録を確かめる。前例は cli.int.test.ts。当初は `sm eval` / `sm feedback` も対象だったが、別の仕様に移した。
- 次のテストは振る舞いが変わるので書き直す: tiers.int.test.ts の「cold は検索に出ない」と、search.test.ts の tier ごとの半減期のテスト。

## Out of Scope

- 定期評価 (`sm eval`)、評価セットの置き場所と形式、週 1 回のフィードバック、通知 (トースト)、定期タスクの追加。別の仕様 docs/specs/rescore-guard-and-temporal-eval.md (別のセッション「評価に基づく個人向け忘却曲線の妥当性検討と設計」) で扱う。そちらでは、`sm eval` を rescore のガードにし、フィードバックをインターリービングで行うことが合意されている。
- 評価の結果から忘却曲線の設定を選ぶ・切り替える仕組み (今は妥当でないと判断済み)。
- リランクを使うときに鮮度を最終の並びに効かせるかどうか (リランクを有効にするときに決める。設計書に未決として書く)。
- 専用の `confirm` ツール (確かめる手間が問題になったら考える)。
- 置き換えられたメモリを get したときの警告。
- 古い記憶の一覧を定期的に知らせる仕組み (必要になったら `sm stale` などから足す)。
- tier と decay の役割の見直し (検索の絞り込みには効かなくなるが、gc と統計のために残す)。

## Further Notes

- 2026-10-17 の評価では、rescore を掛けると nDCG@10 が下がった (0.884 → 今の弱めた値で 0.859)。類似度を主役にする方針は、この結果とも合う。
- cold を検索から外していた理由は、設計書に書かれていなかった。古い情報が混ざるのを避けるためだったと推測し、ユーザーに確かめたところ異論はなかった。
- 今は置き換えられていない cold / archive のメモリが事実上ない (作成日が 10/10 以降のため)。検索の範囲を広げても、当面の検索結果は変わらない。
- `scripts/register-tasks.ps1`、`README.md`、`.gitignore` には、この作業の前からコミットされていない変更がある。実装ではそれを消さずに足す。
