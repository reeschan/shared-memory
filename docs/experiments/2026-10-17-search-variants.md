# 検索設定の比較 (OpenSearch の機能と Sarashina API) 2026-10-17

「OpenSearch 機能の試し方」と「共有メモリ RAG への Sarashina 組み込み 実装方針」の 2 つの資料に沿って、検索の設定を 1 つずつ切り替え、同じ評価セットで比べた結果。本番のエイリアス `memories` とその先のインデックス、本番の Search Pipeline `memories-hybrid` には手を入れていない。再起動が必要な設定は試さず、末尾の TODO に回した。

## 結論

1. **一番効いているのは MCP サーバーの再スコア (時間減衰・アクセス回数・出所)。ただし悪い方向に効いている。** 検索エンジンが返した順位に再スコアを掛けると、nDCG@10 は 0.884 から 0.694 に下がる (60 問中 43 問で悪化)。エージェントが実際に受け取っているのはこの下がった方の順位。減衰とアクセス係数を弱めると 0.859 まで戻る。
2. **Sarashina3 rerank で上位 20 件を並べ替えると、はっきり良くなる。** nDCG@10 は +0.03〜+0.05 (95% 区間が 0 をまたがない)、MRR@10 は 0.99 まで上がる。代わりに 1 クエリあたり約 1 秒かかり、外部 API と 60 RPM の制限に依存する。
3. **RRF は今の min_max 加重平均より悪い** (-0.038、有意)。設計資料 7.2 にある「RRF で統合」は、このデータでは採らない方がよい。
4. **それ以外 (BM25 の k1・b、Sudachi の分割単位、同義語、z_score 正規化、doc2query、Sarashina の埋め込み) は、どれも誤差の範囲。** 60 問では差が出ない。
5. BM25 だけで見ると、**助詞・助動詞を落とす設定** (`sudachi_part_of_speech` の `stoptags`) が有意に良い (+0.032)。現行のテンプレートは `stoptags` を指定しておらず、助詞も索引に入っている。
6. Qwen3-Embedding の検索用 Instruction は外すと大きく下がる (kNN 単独で 0.867 → 0.801、実クエリでは 0.821 → 0.648)。今の設定のままでよい。

## 方法

- 対象: 本番インデックスを `_reindex` で複製した `memory_lab_base` (645 チャンク、うち検索対象 521 チャンク・309 メモリ)。本番と同じく `is_superseded=false` かつ tier が hot / warm のものだけを検索する。
- 評価セット: 60 問 (日本語)。
  - 合成 40 問: 検索対象のメモリから 40 件を抜き出し、Claude が問いを書いた (言い換えた自然文 26 問、エージェント風のキーワード列 14 問)。Sarashina で作ると doc2query と同じ癖が出るので使っていない。
  - 実クエリ 20 問: Query Insights (`top_queries-*`) に残っていた、エージェントが実際に投げたクエリから抜き出した。テスト用のクエリと、答えになるメモリが無いものは除いた。
  - 正解は、BM25 上位 10 件と kNN 上位 10 件を合わせた候補の中から、メモリ単位で 2 (答えている) / 1 (一部関係する) を付けた。候補に入らなかった正解は数えられないので、Recall はやや甘めに出る。判定は 1 回だけで、二重チェックはしていない。
- 指標: メモリ単位 (チャンクの結果を `memory_id` ごとに最大スコアで畳む。本番の MCP と同じ) の Recall@5、nDCG@10、MRR@10。差は、クエリ単位の nDCG@10 の差を 5,000 回ブートストラップして 95% 区間を出した。60 問なので、1 問の差は平均で約 0.017 に当たる。
- 遅延: OpenSearch への検索 1 回の往復時間の中央値。クエリの埋め込み (Ollama / Sarashina) はキャッシュしたので含まない。リランクは API の往復時間を別に出した。
- 環境: OpenSearch 3.5.0 (単一ノード、ヒープ 1 GB)、analysis-sudachi 3.6.0、Ollama `qwen3-embedding:0.6b`、Sarashina API (無償ベータ)。

### MCP の再スコア

本番の MCP サーバーは、OpenSearch の点数に時間減衰 (最終アクセスからの半減期 hot 30 日 / warm 60 日)・アクセス回数 (`1 + ln(1 + 回数)`)・出所の係数を掛けてから並べ替えている (`packages/core/src/search.ts` の `rescore`)。

| 設定 | R@5 | nDCG@10 | MRR@10 | 合成 | 実 | Δ (95% 区間) |
| --- | --- | --- | --- | --- | --- | --- |
| base + 本番の再スコア | 0.839 | 0.694 | 0.741 | 0.681 | 0.721 | **-0.190 [-0.244, -0.136]** |
| base + 弱めた再スコア (減衰の下限 0.7、アクセス係数 0.2 倍) | 0.922 | 0.859 | 0.907 | 0.866 | 0.845 | -0.025 [-0.056, +0.002] |
| base + 出所の係数だけ | 0.933 | 0.872 | 0.911 | 0.886 | 0.844 | |

この評価セットは「話題として合っているか」だけを見ていて、「最近よく使うものを上に出したい」という再スコアの狙いは測れていない。それでも 60 問中 43 問で悪化しており、係数が強すぎるのは確か。アクセス回数の係数は、1 回読まれただけで 1.69 倍、10 回で 3.4 倍になる。

| b = 0 + z_score | | | 0.891 | +0.006 |

`_analyze` で見て分かったこと:

- 現行の `sudachi_part_of_speech` は `stoptags` を指定していないため、何も落としていない (「の」「を」「に」も索引に入る)。
- `sudachi.json` で未知語の品詞を `補助記号,一般` にしているため、`stoptags` に `補助記号` と書くと、`OpenSearch` や `pnpm` のような英字の識別子まで消える。落とすのは `補助記号,句点` / `読点` / `括弧開` / `括弧閉` だけにした。
- `sudachi_normalizedform` は英単語をカタカナにする (`index` → `インデックス`)。日本語で書いたメモには当たりやすいが、識別子そのものでは引けない。standard のサブフィールドを足しても数値は動かなかった。
- 同義語は、Sudachi の正規化と組み合わせると展開されない語や、変な位置で切れる語 (`コンフィグ` → `コンフィ` / `グ`) があった。資料の注意どおり、運用するなら `_analyze` で 1 組ずつ確かめる必要がある。

- **rerank (sarashina3-rerank)**: 今回、はっきり効いた唯一の機能。どの一次検索の上に載せても nDCG@10 は 0.92〜0.94 に揃う。一次検索の差より、リランクの有無の差の方が大きい。
- sarashina3-mini (6 RPM) での doc2query は、生成が約 10 秒 / チャンクで、この文書を書いた時点では生成中。結果は追記する。

### Search Relevance Workbench

3.5 でも `plugins.search_relevance.workbench_enabled` は最初から true だった。REST API だけで Query set (60 問)・Judgment (メモリの正解を全チャンクに展開)・Search configuration を登録し、BM25 系の 3 設定を Pointwise で評価できた (`lab/srw.mjs`)。

| 設定 | NDCG@10 | MAP@10 | Precision@10 |
| --- | --- | --- | --- |
| BM25 現行 | 0.738 | 0.643 | 0.319 |
| BM25 b=0 | 0.728 | 0.625 | 0.304 |
| BM25 助詞等除外 | 0.757 | 0.650 | 0.325 |

チャンク単位で数えるので値は自前の評価と違うが、順序 (助詞等除外が最良) は一致した。分かった制約:

- `POINTWISE_EVALUATION` は 1 実験に 1 設定。比べるなら設定の数だけ実験を作る。
- Search configuration のクエリはテキストの差し込み (`%SearchText%`) だけなので、ベクトルを渡す kNN や hybrid は評価できない。hybrid や Hybrid Optimizer を使うには、`neural` クエリ用に ML Commons へ埋め込みモデルを登録する必要がある (TODO 参照)。

### HNSW

60 問で、HNSW の上位 10 チャンクは総当たり (`script_score`) の上位 10 チャンクと完全に一致した (recall@10 = 1.000、1.2 ms 対 2.1 ms)。645 チャンクの規模では、`m` や `ef_search` を触る意味はない。

## 本番に入れるなら (提案)

すべて再起動なしで入れられる。

1. MCP の再スコアを弱める (コードの変更のみ)。少なくとも、アクセス回数の係数と減衰に下限を付ける。`base+rescore-soft` の形なら -0.19 が -0.025 まで戻る。どこまで弱めるかは、「最近のものを上に」をどれだけ優先したいか次第なので、決めてほしい。
2. 「助詞・助動詞・句読点・括弧を除外」をテンプレートに入れて `pnpm sm reindex`。hybrid では誤差の範囲だが、BM25 単独では有意に良く、害は見えない。
3. Sarashina3 rerank を、オプションとして MCP の検索の最後に入れる (上位 20 メモリ、`task_type: GENERAL_RETRIEVAL`)。+1 秒の遅延と外部送信を受け入れられるかで決める。API が落ちたり 429 を返したりしたら、リランクなしの順位を返す。
4. RRF に切り替えない。統合は min_max のまま (z_score もほぼ同じ)。
5. doc2query と Sarashina の埋め込みは、今の規模では入れない。メモリが増えてから、同じ評価セットで測り直す。

## 外部送信について

Sarashina API の検証で、検索対象を含む全 645 チャンクの本文 (埋め込み・doc2query) と、評価セットの 60 問の問い (埋め込み・rerank) を Sarashina API に送った。無償ベータの規約では、送った内容がモデルやサービスの改善に使われることがある。本番に rerank を入れる場合は、検索のたびにクエリと上位 20 件の本文を送ることになる。
